# Obsidian Spaced Repetition – Architecture Guide

This document reverse-engineers the plugin so future agents can jump straight into relevant modules. Each subsection highlights the responsible classes, their dependencies, and the data that flows between them. File references use the `path:line` format.

## 1. Core Plugin Lifecycle

- **Entrypoint (`SRPlugin`)** – Obsidian loads `SRPlugin` from `src/main.ts:45`. `onload` instantiates helpers (tab manager, next-note handler, sidebar), loads persisted data, initializes the OSR core, and defers the initial sync until the workspace is ready (`src/main.ts:62`). UI chrome such as the ribbon icon, status bar button, and file-menu review entries are also registered here.
- **Command surface** – `addPluginCommands` defines commands for note reviews, global flashcard reviews/cram sessions, and queue-panel management (`src/main.ts:173`). Each command coordinates with `sync()` before invoking modal/tab flows so all derived data structures stay current.
- **Focus & view orchestration** – `registerSRFocusListener` tracks whether a dedicated tab view currently has focus, while `TabViewManager` registers/opens the custom `SR_TAB_VIEW` item and tears down stray tabs at startup (`src/main.ts:314`, `src/gui/tab-view-manager.ts:1`).
- **Plugin data & SRS wiring** – `loadPluginData` merges saved JSON with `DEFAULT_DATA`, upgrades legacy settings, toggles parser debug logging, and calls `setupDataStoreAndAlgorithmInstances` to bind the concrete algorithm and datastore singletons (`src/main.ts:515`). From here on the app talks to `SrsAlgorithm.getInstance()` and `DataStore.getInstance()` everywhere else.

## 2. Vault Sync & Derived State

- **Top-level coordinator (`OsrAppCore`)** – `sync()` delegates to `OsrAppCore.loadVault`, which guards concurrent syncs with `syncLock`, seeds a fresh note graph/review queue/deck tree (`loadInit`), then iterates every markdown file not filtered by `SettingsUtil.isPathInNoteIgnoreFolder` (`src/main.ts:426`, `src/core.ts:88`, `src/core.ts:247`).
- **Per-file processing** – `OsrCore.processFile` pulls note-level schedules from the frontmatter datastore, updates the note-link graph, and only loads notes that carry a flashcard tag or inherit a folder-based deck topic. Matching notes are parsed, converted into `Card` objects, and appended into the root deck tree (`src/core.ts:97`). After parsing, the SRS implementation gets a hook (`noteOnLoadedNote`) to capture per-note ease statistics (`src/core.ts:109`, `src/algorithms/osr/srs-algorithm-osr.ts:73`).
- **Note review queue** – Tags that match `settings.tagsToReview` cause the note to be enqueued into one or more `NoteReviewDeck`s via `NoteReviewQueue.addNoteToQueue` (`src/core.ts:121`, `src/note-review-queue.ts:33`). When a note already has a schedule we store its next due date alongside the tag deck.
- **Finalization** – Once all files are scanned, `finaliseLoad` runs PageRank over the link graph, prunes edit-later cards, filters decks for review vs cram modes, sorts deck names, computes aggregate card stats, and rebuilds both note and flashcard due-date histograms (`src/core.ts:143`). This derived data powers the UI, statistics, and note queue ordering. `onOsrVaultDataChanged` then refreshes the status bar and sidebar if enabled (`src/main.ts:447`).

## 3. Parsing Notes into Cards

- **Text + metadata ingestion** – `NoteFileLoader` is a thin wrapper that instantiates `NoteQuestionParser` with the current settings/default text direction and asks it to return only questions that have topic paths (`src/note-file-loader.ts:20`). Each `Note` caches the raw `ISRFile`, the resulting `Question` list, and helper methods to append cards into decks or persist modified questions (`src/note.ts:6`).
- **Tag & topic resolution** – `NoteQuestionParser.createQuestionList` pre-filters potential notes using cached tag names, then splits the raw file into frontmatter/content, discovers text direction, and builds `Question` instances (`src/note-question-parser.ts:47`). It also analyzes tag positions to create `TopicPathList`s from either frontmatter-level flashcard tags, inline note-level tags, or question-local tags, falling back to folder-derived decks when `convertFoldersToDecks` is enabled (`src/note-question-parser.ts:84`, `src/topic-path.ts:41`).
- **Card extraction** – The Markdown parser (`parse` in `src/parser.ts:82`) recognizes inline separators, multi-line separators, code blocks, and Cloze patterns (delegated to `ClozeCrafter`). Each parsed block becomes a `Question` whose `QuestionText` retains original whitespace, optional topic tag, optional block ID, and the scheduling HTML comment if present (`src/question.ts:184`, `src/question.ts:224`).
- **Schedule hydration & cleanup** – `CardFrontBackUtil` expands reversed and cloze questions into multiple cards, while `StoreInNotes.questionCreateSchedule` reads prior HTML comments (`<!--SR:...-->`) to attach `RepItemScheduleInfo` instances to the resulting `Card`s (`src/question-type.ts:17`, `src/data-stores/notes/notes.ts:21`). Extra stale schedule blobs are trimmed and the question is marked dirty so it can be rewritten once normalized (`src/note-question-parser.ts:102`).
- **Context awareness** – `SrTFile.getQuestionContext` walks the metadata cache headings to capture the breadcrumb for each question, enabling the reviewer UI to show “where in the note” a card came from (`src/file.ts:86`).

## 4. Deck Hierarchy & Flashcard Iteration

- **Deck & topic model** – `Deck` stores hierarchical subdecks, plus two card lists (new/due). Appending a card clones references into every deck indicated by the question’s `TopicPathList`, ensuring multi-tagged questions appear in multiple decks while still pointing back to the same `Card` (`src/deck.ts:170`). `DeckTreeFilter` removes edit-later or postponed cards depending on whether we’re in review or cram mode (`src/deck.ts:308`).
- **Iteration order** – `DeckTreeIterator` destructively walks a cloned deck tree using a configurable deck order/ card order pair derived from settings (`src/deck-tree-iterator.ts:200`). Under the hood a `SingleDeckIterator` handles the per-deck queue (sequential lists, random selection, or fully weighted deck & card randomness).
- **Review sequencer** – `FlashcardReviewSequencer` owns the “current deck/card” pointer, produces deck statistics for the UI, skips cards, and handles review submissions (`src/flashcard-review-sequencer.ts:102`). Review mode triggers `determineCardSchedule`, writes updated schedules back to Markdown via the datastore, adjusts due-date histograms, and optionally buries sibling cards by recording hashes in `QuestionPostponementList` (`src/flashcard-review-sequencer.ts:242`, `src/question-postponement-list.ts:13`). Cram mode simply drops “Easy” cards and loops others to the back (`src/flashcard-review-sequencer.ts:291`).
- **Question postponement** – The postponement list persists hashes in plugin data so subsequent syncs can filter those questions out of the remaining deck tree until the next day (`src/question-postponement-list.ts:24`). `DeckTreeFilter.filterForRemainingCards` consumes the list to remove buried cards from the review queue (`src/deck.ts:313`).

## 5. Scheduling Algorithms & Storage

- **OSR algorithm** – `SrsAlgorithmOsr` implements the only supported algorithm today. It tracks note-level ease values (`NoteEaseList`), analyzes incoming/outgoing links via `OsrNoteGraph`, and combines base ease, link influence (`maxLinkFactor`), and historical flashcard ease to derive the next interval (`src/algorithms/osr/srs-algorithm-osr.ts:17`, `src/algorithms/osr/osr-note-graph.ts:25`). Both note-level and card-level scheduling eventually call `osrSchedule`, which handles response types, modifies ease, and optionally load-balances due dates by looking for the least-populated interval window inside the appropriate `DueDateHistogram` (`src/algorithms/osr/note-scheduling.ts:9`, `src/due-date-histogram.ts:70`).
- **Histograms & stats** – `CardDueDateHistogram` walks the full deck tree to bucket scheduled cards by days-out, while `NoteDueDateHistogram` pulls due dates from every `NoteReviewDeck` and sorts those decks by PageRank-derived importance (`src/due-date-histogram.ts:112`, `src/due-date-histogram.ts:93`). `DeckTreeStatsCalculator` iterates the deck tree to compute aggregate counts, intervals, ease, and “young vs mature” breakdowns stored in `Stats` (`src/deck-tree-stats-calculator.ts:8`).
- **Storage layout** – Note schedules live in YAML frontmatter (`sr-due`, `sr-interval`, `sr-ease`) managed by `DataStoreInNoteAlgorithmOsr` (`src/data-store-algorithm/data-store-in-note-algorithm-osr.ts:31`). Flashcard schedules are serialized back into per-question HTML comments via `DataStoreInNoteAlgorithmOsr.questionFormatScheduleAsHtmlComment`, and `StoreInNotes.questionWrite` rewrites the containing note when cards are added, edited, or rescheduled (`src/data-store-algorithm/data-store-in-note-algorithm-osr.ts:83`, `src/data-stores/notes/notes.ts:63`).
- **Global providers** – `globalDateProvider` and `globalRandomNumberProvider` make it easy to deterministically test scheduling and ordering behavior, and both are used across the SRS and queueing layers (`src/utils/dates.ts:61`, `src/utils/numbers.ts:47`).

## 6. Note Review Workflow

- **Queue model** – Each tag listed in `settings.tagsToReview` gets its own `NoteReviewDeck`, which maintains separate arrays for new notes and scheduled notes, plus the number of currently-due notes (`src/note-review-deck.ts:20`). Sorting uses PageRank scores from `OsrNoteGraph` so more connected notes surface first (`src/note-review-deck.ts:66`).
- **Status surfaces** – `NoteReviewQueue.calcDueNotesCount` tallies due notes so the status bar can reflect how many note reviews are outstanding (`src/note-review-queue.ts:25`). When a note review response is recorded, `OsrCore.saveNoteReviewResponse` recalculates the note’s schedule and updates the queue in place (`src/core.ts:167`). Notes tagged `#edit-later` can still live in the deck tree but will be filtered out of “reviewable” decks by `DeckTreeFilter`.
- **User flow** – `NextNoteReviewHandler` supplies both modal selection and automatic “next note” jumps. It reuses the queue’s ordered decks, honors the `autoNextNote` and `openRandomNote` settings, and opens the chosen `TFile` (`src/next-note-review-handler.ts:28`). `ReviewQueueListView` renders the queue as a nav-tree pane with collapsible sections for new notes, today/tomorrow/yesterday buckets, and future dates, and also wires up context menus via Obsidian’s `file-menu` event (`src/gui/review-queue-list-view.ts:1`).
- **Sidebar integration** – `OsrSidebar` registers the review queue view type and, if configured, opens it by default when Obsidian starts (`src/gui/sidebar.ts:23`). The sidebar also watches for vault events (file open/rename) so it can re-render once derived data changes.

## 7. User Interfaces

- **Flashcard modal & tab** – `FlashcardModal` hosts both the deck list (`DeckUI`) and the flashcard view (`CardUI`). The modal enforces the configured height/width percentages and toggles between the decks list and the active flashcard (`src/gui/sr-modal.tsx:17`). `SRTabView` embeds the exact same UI in a workspace tab by lazily loading the sequencer via `TabViewManager` callbacks (`src/gui/sr-tab-view.tsx:28`).
- **Deck UI** – `DeckUI` renders a tree mirroring the deck hierarchy from the original deck tree, shows summary counts (due/new/total), and uses `reviewSequencer.getDeckStats` plus `TopicPath.emptyPath` queries to refresh stats before each show (`src/gui/deck-ui.tsx:20`). Clicking a deck kicks off `startReviewOfDeck`, which sets the sequencer’s current deck and, if cards are available, switches to the flashcard view.
- **Card UI** – `CardUI` drives the actual review experience: it tracks which decks are currently being reviewed, renders Markdown for the front/back via `RenderMarkdownWrapper`, enforces the “show interval” preference, implements keyboard shortcuts, and dispatches review responses to the sequencer (`src/gui/card-ui.tsx:1`). It also provides reset/edit/skip actions and supports delayed answer buttons via `settings.reviewButtonDelay`.
- **Statistics & settings** – `StatisticsView` uses Chart.js + Grid.js to visualize forecasted card loads, interval distributions, ease distributions, card type ratios, and note-level ease tables (fed by `SrsAlgorithm.getInstance().noteStats()`) (`src/gui/statistics.tsx:1`). `SRSettingTab` defines grouped tabs for settings categories (flashcards, notes, scheduling, UI, stats, help), saving changes through `plugin.savePluginData()` and toggling parser debug logging (`src/gui/settings.tsx:17`).
- **Localization & icons** – All UI strings come from the translation helper `t()` and the locale files under `src/lang`, so any copy updates must go through the translation keys. `appIcon()` registers the custom “SpacedRepIcon” used across the plugin (`src/main.ts:107`).

## 8. Settings, Persistence, and Data Contracts

- **`SRSettings` schema** – Defined in `src/settings.ts:3`, the settings struct spans flashcard parsing options, UI presentation, scheduling knobs (base ease, easy bonus, maximum interval, load balancing), data storage preferences, and logging flags. `upgradeSettings` performs ad-hoc migrations (e.g., when deprecating `randomizeCardOrder`), and helpers like `SettingsUtil.isFlashcardTag` centralize tag matching.
- **Persisted plugin data** – Stored via Obsidian’s `Plugin.saveData`, a `PluginData` object keeps the current settings snapshot, the last day the bury list was cleared, hashes for buried cards, and the last deck history entry (`src/plugin-data.ts:3`). `QuestionPostponementList.write()` calls back into `savePluginData` whenever the bury list changes so the postponed set survives restarts.
- **Filesystem contracts** – `SrTFile` wraps Obsidian’s `TFile`, injecting helpers for reading frontmatter, listing tags (including frontmatter-only tags), retrieving text direction, and providing question context from the heading stack (`src/file.ts:1`). This wrapper is used everywhere the plugin reads or writes Markdown so tests and future storage swaps need only adjust a single abstraction.

## 9. Supporting Utilities & Build

- **Topic paths & tagging** – `TopicPath` converts tags (e.g., `#flashcards/maths/algebra`) or folders into hierarchical paths that decks understand (`src/topic-path.ts:1`). `TopicPathList` groups multiple paths together and offers helper methods for filtering valid paths relative to settings.
- **Parsing helpers** – `utils/strings.ts` includes regex-escaping, whitespace-preserving operations, frontmatter splitting (keeps blank lines so line numbers remain accurate), code-friendly string replacement, and hash generation (`cyrb53`). These helpers are used across parser, question formatting, and note rewriting routines.
- **Rendering & assets** – `styles.css` defines the modal and pane look and feel, while `icons` declares the SVG icon used via `setIcon`. The plugin bundles via `esbuild.config.mjs`, which targets `src/main.ts`, excludes Obsidian/electron/builtin modules, and outputs to `build/main.js` for packaging (`esbuild.config.mjs:1`).
- **Tooling/tests** – TypeScript configuration (`tsconfig.json`), ESLint/Prettier configs, and Jest (`jest.config.js`) are set up so you can run linting/testing via the `pnpm` scripts in `package.json`. Unit tests live under `tests/` and rely on the helpers in `src/utils` plus mock data for parser/scheduling scenarios.

## 10. End-to-End Flow Cheat Sheet

1. **Startup** – `SRPlugin.onload` loads settings/data, registers UI, initializes `OsrAppCore`, and schedules a `sync()` when the workspace settles (`src/main.ts:62`).
2. **Sync** – `OsrAppCore.loadVault` walks every markdown note, `NoteQuestionParser` extracts questions/cards, the SRS algorithm updates note stats, and the app rebuilds deck trees, note queues, histograms, and stats (`src/core.ts:88`).
3. **Review flashcards** – User invokes a command or clicks the ribbon/status bar. `TabViewManager` or `FlashcardModal` requests a `FlashcardReviewSequencer`, which clones the deck trees, iterates cards according to settings, records schedules, and optionally buries siblings (`src/main.ts:223`, `src/gui/sr-modal.tsx:17`, `src/flashcard-review-sequencer.ts:230`).
4. **Review notes** – The sidebar or command palette shows the tag-based queue built during sync. `NextNoteReviewHandler` picks the next file (respecting randomness/auto-next), opens it, and `SRPlugin.saveNoteReviewResponse` writes schedules + updates histograms/bury lists when the user answers via the file menu or command palette (`src/next-note-review-handler.ts:43`, `src/main.ts:487`).
5. **Settings & stats** – The settings tab lets users tweak parsing, deck ordering, UI sizing, or algorithm knobs, all persisted via `savePluginData`. The statistics tab fetches the latest deck stats/due-date histograms from `OsrAppCore` for visualization (`src/gui/settings.tsx:40`, `src/gui/statistics.tsx:33`).

Armed with this map you can quickly navigate to the relevant subsystem—UI, parsing, scheduling, datastore, or queue—to implement new features or investigate bugs.***
